How a 16-year-old race in SQLite's WAL survived until Tailscale checkpointed too hard

2026-08-13▲ 566tailscale.com ↗94 comments ↗

Player not loading? Open the explainer on Scrimba ↗

SQLite is often held up as the most heavily tested piece of software most of us will ever run. So when Tailscale published a postmortem tracing months of database corruption to a race condition that had been sitting in SQLite's write-ahead log code for at least sixteen years, it hit the top of Hacker News fast. The story has everything: an unreproducible bug, production-only telemetry, the SQLite team building custom debugging tooling, and a fix that landed upstream in SQLite 3.51.3.

Nineteen corruptions, zero pattern

Starting last August, Tailscale's control plane suffered 19 separate SQLite corruption incidents over six months. Each one forced them to halt the affected shard, so tailnets on it lost access to the admin console and API until a backup was restored. The usual debugging playbook went nowhere: no correlation with deploys, customers, load, or hardware, and the failures were sometimes hours apart, sometimes weeks. Synthetic reproduction attempts all failed.

The first real clue came from infrastructure built for recovery rather than debugging. To shrink restore times, Tailscale had started streaming every SQL modification to a separate transaction log. SQLite is single-writer with serializable transactions, so replaying that log against a known-good backup should reconstruct the database exactly. Instead, replay exposed something that should be impossible: data committed by one transaction was invisible to later transactions. That ruled out application bugs and pointed squarely at the storage layer.

The race inside the checkpoint

In WAL mode, SQLite doesn't modify the main database file on every write. Transactions append changed pages to a separate write-ahead log, and a periodic checkpoint copies those pages back into the main file, after which the WAL can be reset and reused. Tailscale runs an unusual configuration: they take manual control of checkpointing and run it aggressively, which lets them do fast, consistent backups.

Working with SQLite's professional support team, they got a purpose-built debugging tool: a shim called tmstmpvfs that wraps SQLite's virtual filesystem layer and traces low-level disk operations. The traces revealed the fatal interleaving. If a write transaction commits and resets the WAL at one precise moment during a checkpoint, the checkpointer gets confused: it marks pages as already copied into the main database when they never were. No error is raised. The pages are simply lost, and later transactions write pages that reference the missing ones — a silently inconsistent, corrupt database.

The window is only a few instructions wide, which is why the bug hid for sixteen years. Most applications let SQLite checkpoint automatically and never hammer that code path; some VFS configurations use exclusive locking and bypass the vulnerable shared-memory coordination entirely. Tailscale's aggressive manual checkpointing made the collision statistically inevitable. The fix in SQLite 3.51.3 is a check rather than a redesign: the checkpoint function now detects that another thread has reset the WAL underneath it and bails out instead of losing pages.

Fifteen minutes versus sixteen years

The best detail in the HN thread comes from Antithesis, the deterministic-simulation-testing company: they report their system finds this exact bug in roughly fifteen minutes, because simulation explores thread interleavings systematically instead of waiting for production traffic to stumble into a few-instruction window. Another commenter pointed to a TLA+ model of WAL checkpointing that independently rediscovered the same flaw through formal methods. Sixteen years of real-world usage and one of the industry's most rigorous test suites missed what schedule exploration finds before lunch.

There's a satisfying epilogue, too. Tailscale instrumented their SQLite driver to log a warning — named SQLitePartyMode — whenever a write and a WAL reset overlap. Two months after deploying the fixed SQLite, the warning fired and no corruption followed: direct evidence the patch prevented an incident that would previously have destroyed data.

Who should care

If you run SQLite with default settings, you were almost certainly never at risk, but upgrade to 3.51.3+ anyway. The broader lessons travel further. Running boring technology in a non-standard way — here, manual aggressive checkpointing — moves you onto paths the ecosystem hasn't tested for you. Transaction-log replay is a cheap way to turn "the database is corrupt" into "here is the exact impossible state," and it's worth building before you need it. And for anyone maintaining concurrent code: races this narrow are found by deterministic simulation or formal modeling, not by waiting. Sixteen years of production traffic is a worse fuzzer than fifteen minutes of the right tool.
